# POFlow — منصة أوامر الشراء والتوقيعات والموافقات الإلكترونية · v1.5

**Purchase Order Approval & Digital Signature Platform** — الإدارة التنفيذية للاتصالات وتقنية المعلومات · مركز العمليات التقنية ITOC · جامعة سليمان الراجحي

منصة تشغيلية متكاملة (وليست نموذجًا أوليًا) تدير دورة حياة أمر الشراء: من إنشاء الطلب في **النموذج الرسمي (Purchase Requisition)**، إلى توقيع الجهة الطالبة، فمراجعة المشتريات وتحديد المسار وفق **مصفوفة الصلاحيات**، ثم **التوقيعات المتسلسلة** والرفض، وانتهاءً بنسخة **PDF نهائية** موقّعة ومؤرشفة وقابلة للتحقق.

> **منطق التوقيع = منطق منصة السياسات (v3.4) نفسه:** سجل توقيعات مشفّر مستقل وخاص بالمنصة، تشفير الصورة داخل المتصفح (AES-256-GCM بمفتاح PBKDF2 من الرقم السري)، لا يصل الرقم السري إلى الخادم، قفل بعد 5 محاولات، بصمة SHA-256 للمحتوى في كل توقيع، طرق العرض (ختم · صورة · مموّهة)، زرا «توقيعاتي» و«كيفية التوقيع»، النسخة النهائية مع شهادة توقيع ورمز QR وصفحة تحقق.

```
ictsru.github.io/POFlow  →  Google sign-in (@sr.edu.sa)  →  Apps Script Web App  →  Google Sheet «سجل أوامر الشراء - POFlow» + Drive (خاص)
     صفحة دخول ITOC                صفحة Google نفسها           تحقق من الحساب والدور في كل عملية
```

## دورة العمل
| # | المرحلة | من | ماذا يحدث تلقائيًا |
|---|---|---|---|
| 1 | إنشاء أمر الشراء | الجهة الطالبة | النموذج الرسمي، جدولا المستهلكات/الخدمات والأصول، الإجماليات، اقتراح المسار حسب مصفوفة الصلاحيات، رفع المرفقات |
| 2 | توقيع الجهة الطالبة (يعد) | مدير إدارة الجهة الطالبة | بريد + إشعار له فقط؛ بعد التوقيع يُحال الطلب **تلقائيًا** للمشتريات |
| 3 | مراجعة المشتريات | إدارة المشتريات | الرقم التسلسلي، توجيه المشتريات، الموعد المستهدف، الموقّعون **بالترتيب** وموضع كل توقيع (الجدول × يعد/يقترح ويوصي/يعتمد/يعلم)، أو **إعادة للاستكمال** |
| 4 | التوقيعات المتسلسلة | الموقّعون | الطلب يصل للأول فقط، ثم للتالي بعد كل توقيع دون تدخل يدوي؛ **الرفض** بسبب إلزامي يوقف الدورة فورًا ويبلّغ المشتريات والجهة الطالبة |
| 5 | الاعتماد النهائي | النظام | «مكتمل ومعتمد»، PDF نهائي (النموذج + مصفوفة الصلاحيات + شهادة التوقيع وQR)، أرشفة في Drive، بصمة الملف، إرسال للمشتريات والجهة الطالبة والموقّعين و«يعلم» |

## إدارة المستخدمين والصلاحيات (v1.3 — RBAC يتحقق منها الخادم)
**الدخول مقصور على المستخدمين المفعّلين في ورقة `AllowedUsers`.** أي حساب جامعي آخر تظهر له شاشة **«لا تملك صلاحية الدخول»** مع نموذج **طلب صلاحية الدخول** (الاسم، الصلاحية المطلوبة، السبب)، فيُرسل الطلب بالبريد إلى **m.elmahdy@sr.edu.sa** (`ACCESS_ADMIN_EMAIL`) ويُسجّل في ورقة `AccessRequests`، ويظهر لمدير النظام في «المستخدمون والصلاحيات» للموافقة (مع اختيار الصلاحية) أو الرفض، ويُبلَّغ مقدم الطلب بالقرار بالبريد.

| الدور | `role` | الصلاحيات |
|---|---|---|
| مدير النظام · **Admin** | `admin` | كل شيء: المستخدمون وطلبات الدخول والتفويض والإعدادات وطريقة عرض التوقيع + صلاحيات المشتريات |
| محرر · **Editor** | `editor` | إنشاء الطلبات وتعديل مسوداته وإرسالها، والتوقيع أو الرفض على الخطوات المسندة إلى بريده |
| محرر + فريق المشتريات | `editor` + ☑ `procurement` | ما سبق + جميع الطلبات، المراجعة والإعادة، تحديد/تعديل المسار، بدء الدورة، إصدار النسخة النهائية |
| مشاهد · **Viewer** | `viewer` | اطّلاع فقط: جميع الطلبات والأرشيف والتقارير والتحقق وسجل التدقيق — دون إنشاء أو توقيع |

القيم القديمة تُقرأ تلقائيًا: `procurement` ← Editor + المشتريات · `requester`/`signer` ← Editor · `auditor` ← Viewer.
مالك المنصة (`OWNER_EMAILS`) مسموح دائمًا ودوره Admin. للعودة إلى فتح المنصة لكل الحسابات الجامعية: `ACCESS_MODE = 'DOMAIN'`.

التوقيع مرتبط **ببريد كل خطوة** (وليس بالدور فقط)، مع **تفويض مؤقت** محدد المدة يظهر في المستند «بالنيابة عن».

## التشغيل لأول مرة (≈15 دقيقة)
1. افتح الجدول «سجل أوامر الشراء - POFlow» (الرابط أعلاه) ← Extensions ▸ Apps Script.
2. أضف الملفات: `Code.gs` · `Demo.gs` (Script) و`Index` · `HowTo` · `Logos` · `CompanyLogo` · `PdfFont` · `Denied` (HTML)، والصق `appsscript.json` (Project Settings ▸ Show manifest).
3. شغّل الدالة **`setup`** مرة واحدة ووافق على الصلاحيات (Sheets · Drive · Gmail · Triggers). تُنشأ الأوراق والمجلدات الخاصة والمفتاح السري ومشغّل التذكير كل ساعة.
4. **Deploy ▸ New deployment ▸ Web app** — Execute as: **Me** · Who has access: **Anyone within Sulaiman Al Rajhi University**.
5. افتح المنصة ← **الإعدادات**: بريد المشتريات، بريد التصعيد، **دليل المناصب** (مدير المشتريات، المستودعات، المرافق، المالية، الرئيس التنفيذي للخدمات المشتركة، مدير الشركة) — منه يُقترح المسار تلقائيًا.
6. **المستخدمون والصلاحيات**: أضف المستخدمين (Admin · Editor · Viewer)، وفعّل «فريق المشتريات» لمحرري إدارة المشتريات. البقية يطلبون الصلاحية من شاشة الدخول.
7. رابط `/exec` مضاف في `CONFIG.WEB_APP_URL` داخل `index.html` — ارفع المستودع `ICTSRU/PR` (Pages: main / root).
8. التحديث التلقائي مفعّل في `ICTSRU/PR` (انظر أعلاه و**AUTODEPLOY.md**).
9. أضف الرابط إلى ITOC Index (ورقة Links).

## الأمان والحوكمة
- الدخول بحسابات `@sr.edu.sa` فقط، والتحقق من الحساب والدور **في كل استدعاء** (`poApi`)، وتسجيل الدخول في `AccessLog`.
- سجل تدقيق `AuditLog` لكل إجراء (إنشاء، حفظ، إرسال، توقيع، رفض، إعادة، مسار، تفويض، تحقق…) — للإضافة فقط ومحمي من التعديل.
- منع تكرار التوقيع على الخطوة نفسها، ومنع التوقيع خارج الدور، وفحص التعارض (`baseUpdatedAt`) و`LockService` عند كل كتابة.
- **بصمتان:** `contentHash` للطلب (يوقّعها مدير الجهة الطالبة) و`fullHash` للطلب + الرقم التسلسلي + توجيه المشتريات (توقّعها سلسلة الاعتماد). تعديل مسار الخطوات اللاحقة لا يُبطل التوقيعات السابقة.
- التشفير أثناء النقل (HTTPS) والتخزين (Google Workspace)، وصور التوقيع مشفّرة دائمًا في السجل.
- **تمييز قانوني:** التوقيع في المنصة **توقيع إلكتروني بسيط موثّق** (هوية جامعية + رقم سري + سجل تدقيق + بصمة)، وتنص شهادة التوقيع على ذلك صراحة. خانة `DIGITAL_PROVIDER` محجوزة لربط مزود توقيع رقمي معتمد مستقبلًا.
- **الاستمرارية:** كل خطوة تُحفظ فورًا على الخادم؛ انقطاع الاتصال لا يفقد شيئًا، وإن فشل إصدار PDF في متصفح آخر موقّع يظهر زر «إصدار النسخة النهائية» للمشتريات والموقّعين.
